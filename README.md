# 积微 · JiWei

一个微信窗口装下所有琐碎：文章收藏、日程、待办、灵感想法、报销记账。发进来就自动分好类，每天早上给你一份提要，周日压成一页周报。积微成著，数据全在本机。

DeepSeek Harness 的两个插件 + 一层本地文件。微信收发、网页抓取和模型调用需要网络，其余都在本机。

> 积：攒起来，压实。微：碎片、微小，也指微信。名字取自「积微成著」——攒够碎片，才看得见东西。

---

## 一句话能做什么

| 你说 | 它做 |
| --- | --- |
| 转发一篇公众号文章 | 进阅读收件箱，自动解析标题，同一链接不重复收录 |
| 点评 | 读收藏的正文，每篇三百字内点评，直接发回微信 |
| 明天九点见客户 | 记成带时间的事项，第二天早上出现在提要里 |
| 报销发票 + 一张 PDF | 存下文件，认出商家和金额 |
| 我有几个待办报销 | 直接数给你，不用翻面板 |
| 补进去：这是打车费 | 并进原来那条，不重开一条 |
| 取消刚才的保存 | 撤销刚才存下的附件或收藏 |
| /发 发票 | 把电脑上存着的附件直接发回微信 |

## 它解决什么问题

碎片化信息管理的失败，通常不是因为「没记下来」，而是三件事：

1. **只进不出。** 消息、链接、想法越攒越多，从来没有一步把 N 条原始记录变成 1 条当前状态。于是「最新的到底是什么」只能靠脑子维护。
2. **每次整理都在重新设计系统。** 上一次的分类、上一次的模板，这次不用了。坐标系一漂移，累积归零。
3. **系统和你的判断混在一起。** AI 把你一句「觉得这方法有点旧」写成了项目结论，你下次看到会愣住：这是我说的，还是它编的？

这套东西的三个对应设计：**压实**（compaction）、**规则文件化**、**证据与结论分离**。

## 三个层次

| 层 | 是什么 | 存在哪 | 你看它的频率 |
| --- | --- | --- | --- |
| **S1 原始材料** | 聊天原文、转发、文件变动 | `capture/<日期>.jsonl` | 只在核对时 |
| **S2 当前状态** | 每个项目**现在**的样子 | `projects/<项目>.md` | 每天 |
| **S3 长期理解** | 你写下的判断、经验、未决问题 | 本子 + 项目「未决」 | 想起来才看 |

S1 可以很多，**S2 必须少**，S3 必须是自己写下来的话。

---

## 四个节奏

| 时机 | 做什么 |
| --- | --- |
| **收到消息** | 当场分诊：分类、抽时间、归位，回复「已执行的操作 + 保存的内容」 |
| **每天早上** | 早间提要：今天几件事、最早几点，带上时间与地点；没有安排就说没有 |
| **每晚** | 语义收口：找「做完了 / 没改善 / 决定用 X」，关任务、更新项目状态 |
| **每周日** | 压实：合并重复、改写四问、出一页周报（收藏只留一行摘要） |

微信消息默认交给 **DeepSeek Harness 已配置的 LLM** 判断意图：明确的待办和想法直接保存，普通聊天直接回复，意思不确定时先追问确认。模型调用或校验失败会提示错误，不把聊天降级成记录。匹配已有任务的收尾、项目结论更新和每周压实仍由定时 Agent 核对证据后执行。

## 数据流

```
微信 ──> reading-inbox ──> Harness LLM 分类
                               │
                               ├─ 聊天 / 追问 ──> 直接回复
                               ├─ 收藏链接 ────> 阅读收件箱
                               ├─ 意图不明确 ──> 追问 → 用户确认 / 补充
                               └─ 待办 / 想法 <────────┘
                                      │
                                  Python 校验
                                      │
                       原话与确认答复 → capture/<日期>.jsonl
                       实际新增条目 ──> store.json → 结果回执
                                          │
                              面板 + 定时任务（收口/压实）
```

模型通过 Harness 的 `ctx.llm` 服务调用，复用已配置的认证，不需要另外填写 API Key。默认跟随账本定时任务所属会话的模型（优先晚间收口，其次周报、兜底扫描），读取该会话最新选择；你在 Harness 切换这个会话的模型后，微信也随之切换。没有账本定时任务时，再按当前调用者、近期对话、Harness 默认、已有会话和可用服务选择；自动选择会跳过没有可用模型的服务。多个可用服务无法确定优先项时会提示选择，也可显式指定，见 [安装说明](INSTALL.md#llm-配置)。模型调用会把消息、近期对话和账本快照发送到选定服务。

晚间和周报模板调用 `reading_journal_review`，由 LLM 返回带逐字引用的发现、本子回应和下一步建议。工具只返回建议；Agent 继续通过原有 `evidence`、`notebook-review` 等命令保存，成功后才推送。`reading_journal_llm_status` 可查看模型服务和最近调用状态。

## 保存结果如何反馈

回执先说明实际结果，例如“已加入待办：整理结果”“已保存想法：调整实验方案”“已加入阅读收件箱：《文章标题》”。时间、截止、地点和关联项目会明确标注；没有项目的待办仍是已保存的待办，界面显示“未关联项目”。

重复消息会说明“未重复添加”，并反映记录的当前状态。只保存答复但未改任务时会明确说“任务尚未修改，待核对”。通知数量按实际新增条目显示，资料收藏不再承诺未经确认的整理时间。

## 在微信里聊天

默认无需命令，可以直接给已绑定的机器人发消息。模型会读取当前账本快照，保留最近 20 轮对话，重启后也能接着聊。

| 消息例子 | 处理方式 |
| --- | --- |
| 明天交报告 | 新增待办，回复“已加入待办：交报告”及截止日期 |
| 我怀疑样本量不足 | 保存想法，回复“已保存想法：样本量可能不足” |
| 我明天有哪些安排？ | 依据账本回答，不新增记录 |
| 这个也许值得做 | 先问清楚具体内容、是否记录；确认后才保存 |

待确认提议会显示拟保存内容，并标明“尚未保存”。只有问题成功发送后，后续答复才可触发保存；含糊的“好”不能代替具体选项。确认会保留原话与补充消息各自的时间，避免跨日后把“明天”算错。提议 24 小时后失效，切换模式或清空对话也会取消提议。

| 消息 | 作用 |
| --- | --- |
| `/聊天` | 进入纯聊天模式，暂停自动记账 |
| `/记 明天整理结果` | 单独记一条，聊天模式保持不变 |
| `/退出` 或 `/退出聊天` | 退出聊天，回到自动分诊模式 |
| `/新对话` | 清空对话上下文和待确认提议，保留账本及当前模式 |

自动模式中的聊天和待确认内容不进入账本证据，晚间扫描也会跳过。`/聊天` 模式中的所有普通消息及链接都只参与对话，需要保存时使用 `/记`；`/退出` 恢复自动识别。模型不能直接完成任务或改写项目，需要改状态时在面板操作。没有联网搜索和执行命令能力。账本较大时只提供部分上下文，不能当作完整检索。明确使用 `/记` 时保留规则兜底；管理员通过 `--no-llm` 禁用模型后，普通消息恢复规则记账。

对话保存在数据目录 `conversations/`，与原始账本证据分开；仅接受扫码绑定用户的消息。聊天使用 Harness 同一模型服务，近期对话和相关账本快照会发送到该服务。

## 四条硬规则

Agent 的整理规则写在数据目录的 `RULES.md` 中；修改规则不会自动改变 Python 的正则分诊逻辑。仓库 `journal/RULES.md` 是首次安装模板。最要紧的四条：

**1. 机器绝不改写你的本子。** 会被系统改写的本子，人就不敢认真写。

**2. 项目文件里，机器只重写两个标记之间。**

```markdown
<!-- journal:managed -->
## 要解决
## 现在
## 下一步
## 未决
<!-- /journal:managed -->

## 我的理解      ← 这一段机器只读，永不碰
```

找不到标记就**拒绝改写**，绝不覆盖。

**3. 证据必须带逐字引用。** 想把一段材料写进项目进展，必须给出来源里真实存在的原话，否则闸门拒绝。文件变动只能记成「观察」，不能据此改结论。

**4. 冲突永不自动合并。** 两侧都改过，就报出来让人选。自动合并会把两个都合理的改动揉成一个都不对的版本，而你看不出它揉过。

## 安装

```
git clone https://github.com/CRYPTOCHROME384/jiwei.git
cd jiwei
node install.mjs
```

然后两件事：**重启 DeepSeek Harness**，再让 agent 按 `schedules-ready.md` 建四个定时任务（安装器会打印路径）。

默认账本目录 `~/.dsh-journal/data/`，可用 `--data` 指定。装完是**空账本**，没有任何示例数据。

详见 [INSTALL.md](INSTALL.md)。

## 目录

```
plugins/reading-inbox/   微信通道 + 阅读收件箱（链接、文献）
plugins/journal-panel/   面板（今天 / 待办 / 项目 / 本子 / 想法 / 活动）
journal/                 journal.py 及模块，规则文件 RULES.md
templates/               数据目录的空骨架
install.mjs              安装器（幂等）
```

`journal/` 是代码，数据目录是数据——**两者可以分开放**，安装器会把 `.py` 复制进数据目录，让数据目录自包含、可整包备份。

## 一些取舍

**不做正文的双向同步。** Markdown 和结构化块之间往返会掉格式，第一次同步就会把你写的东西改形。字段可以双向，正文只单向。

**只有三种类型**（任务 / 想法 / 资料），不新增。类型多了分类就失去意义——分类只回答「该进哪条流水线」，不负责让你「找到」东西，找东西靠搜索。

**不为收藏生成待办。** 「这篇文章挺有意思」是线索，不是任务。只有它回答了一个问题、或者你写下了理解，才值得再走一步。

**不给静默赋予含义。** 任务没勾完成不等于没做，长期没提到不等于放弃。系统只能问「要不要暂缓」，不能替你判定。
